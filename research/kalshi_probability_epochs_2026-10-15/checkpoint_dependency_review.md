## Data-size and copy dependencies

Practice model.to_state (`speeddesk_model.py:1208`) rebuilds windows, inventory, orders, closed settlements, sorted cohort sets, seen trades, consumed levels and Bitcoin price maps. It also returns references to mutable days/venue_days/history dictionaries. Runner state retains references to reports, coverage, latency, observed and evidence dictionaries/lists. WindowEvidence.state (`speeddesk_metrics.py:200`) returns aliases; its advance path prunes detailed evidence at 31 days, while practice model history and report iteration have no corresponding checkpoint-level bounded archival cut. Retention is intentional history, not disposable data.

For D report days, V venues, W windows and C closed settlements, the repeated conversion work includes roughly D*V full-settlement conversion passes plus window scans, with further current-panel passes. Scorecard grouping already has its own optimization/tests; do not duplicate or undo it. This is a source-derived complexity observation, not a measurement of production sizes. Ledger normalization rebuilds container trees; mirror encoding traverses the state again. Reports are represented both at state top-level and inside panel, so output itself contains repeated logical history. Removing fields or changing persistence layout is a schema/restore change, not a free serialization fix.

Live state keeps active windows separate from cold archive chunks after one hour, but twin state and evidence/report payloads are still built. Full mirror reconstructs archived+active history maps and panel. `_live_windows` / `_cold_windows` scan retained orders/fills; history size can affect state construction even where output is archived. Exact production state bytes, row counts, JSON allocations, RSS and WAL/disk contribution were not supplied by these three spans.

A blanket `to_thread(checkpoint)` is unsafe: state contains mutable aliases, checkpoint mutates pending/journal/archive/stop fields, SQLite transaction nesting is connection-wide, and live accounting assumes one writer. Copying everything first preserves a substantial on-loop cost and raises peak memory; a thread can still contend for the GIL. Async/coalesced writers, relaxed sync, delayed reports, deleting history or changing source hashes are outside this task.

## Critical durability and accounting boundary

Practice receipts.db is separate from real companion receipts.db. Practice uses SQLite WAL NORMAL after a FULL first save on a fresh ledger; the first full sync must precede the unsynced mirror. Missing ledger beside an existing report fails closed. Process-crash recovery is different from host/power-failure durability; preserve both existing contracts. Practice history/counters cannot be reset to make saves small.

Real order `_journal_intent` (`speeddesk_live.py:1011`) stores client ID, complete reservation, window terms and bootstrap identity with FULL durability BEFORE the first create network byte (`:2002` onward). A definite no-send refusal may rewrite with NORMAL; uncertainty retains full reservation. No order retry, release or accounting inference may depend on a display copy. A full checkpoint atomically saves receipts, optional archive chunk, state and empty journal; journal/dirty/archive memory clears only after commit. This atomic boundary is essential even though ordinary reconcilable account facts use NORMAL.

FULL is retained for startup, shutdown, pre-send journal and OWNER_RECORDS (day reset, integrity reset, resume and stop). Immediate fill/settlement/release/stop-owner save behavior, the one-second dirty-save bound and five-second quiet bound stay unchanged. Stop latch and receipt must persist together; consumed controls, loss totals, foreign-owner isolation, uncertain reservations, archives and reconciliation proof remain intact. Day stop does not justify simplifying live paths: legitimate risk reduction, reconciliation and cancellation can remain relevant. No restart/resume is authorized here.

## Ranked optimization candidates — hypotheses only

1. **Reuse immutable report input conversions within ONE existing practice checkpoint.** First profile separately the repeated window/settlement `asdict` preparation from actual scorecard aggregation. If material, consider checkpoint-local prepared dictionaries reused by historical summaries and panel, while retaining each summary's filtering, clock/cutoff evaluations, report ordering and correction logic. No cross-checkpoint cache, new writer, reduced cadence or model edit. Savings are unknown. The lifecycle must discard prepared inputs at checkpoint end, never persist them or reuse after mutation/restart. Explicitly preserve independent report result containers and never let report code mutate shared prepared rows. Wall-clock boundary behavior requires tests; replacing multiple current clock calls by a frozen timestamp is not silently equivalent.
2. **Reduce redundant normalization/encoding of already-native practice state.** Evidence shows costly practice_ledger but does not isolate conversion from SQL/COMMIT. Profile first. A specialized strict native-state serialization route may avoid a recursive container copy; shared ledger fast paths affect every desk and are wider money-sensitive work. Native-only validation, float/key/subclass/unsupported/deep recursion behavior, exact stored value, failure timing and transaction semantics all matter. Do not simply reuse mirror JSON: ledger currently normalizes/stringifies keys and permits behaviors that mirror allow_nan=False rejects. Keep this behind candidate 1 and do not bypass canonical receipt hashing.
3. **Checkpoint-local model/state conversion improvements.** Profile exact `asdict`/state-building share; a validated direct serializer or reused immutable conversions may help. Changing speeddesk_model.py impacts both trading/model semantics and observer fingerprints, so this is not the smallest first patch. Preserve complete model golden state/restore, dataclass behavior and all histories. No pruning/archive migration in this pass.
4. **Live-only display/state preparation.** Keep as a separate follow-up only if fixed recurrence and offline profiling show material costs after practice work. Existing one-write mirror optimization already exists. Future prepared summary reuse or narrower active/history scans must pass live archive/reopen/crash tests; never move journal/state writes or alter save triggers. Stronger money-sensitive review required.

Not selected: async writer/process migration, practice checkpoint coalescing, longer save/report/mirror intervals, weakening fsync, deleting reports/history, swapping JSON libraries blindly, or engine-wide changes. These introduce wider semantics without a uniquely attributed cause.
