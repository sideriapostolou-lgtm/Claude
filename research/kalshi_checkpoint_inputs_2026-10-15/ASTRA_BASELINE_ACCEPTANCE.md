## Candidate safeguards and acceptance gates

* Scope only existing settlement-conversion callsite in practice summaries plus minimal checkpoint-local lifetime plumbing. Keep mutable windows, venue filters, all clock calls/order, scorecard formulas/grouping, coverage, latency, daily evaluation/correction order, serializers, model.to_state and all financial paths unchanged.
* Lazy conversion at the original row position; no eager whole-history pre-pass that moves exceptions ahead of earlier daily receipts. Reuse only exact native frozen Settlement rows with verified native scalar contents, or a safe scalar-signature check; original asdict fallback for exotic/malformed/subclass rows. Frozen annotation alone is not runtime validation. A same-object field can be changed through object.__setattr__, and closed-list order/content may change without length change. Preserve duplicate/conflicting rows.
* A fresh result list each summary; cached dictionary ownership must not permit a consumer to mutate another summary's inputs. Prefer fresh shallow copies of flat cached dictionaries if necessary for equivalence; measure their cost. Signature checks and dictionary copies can eat savings; count reduction alone is insufficient.
* No across-checkpoint cache. Context ends on every exception/success; standalone summary/panel/daily_reports and constructor migration remain fresh. Nested invocation needs explicit isolation/invalidation, not blindly restoring stale outer cache after inner mutations. No thread, asynchronous writer, detached task, persistent queue or larger state schema.
* Differential tests must compare full persisted state and mirrors, ordered normalized receipts/hash chains, pending state on failure, timestamps and correction receipts. Identical scripted clock sequences should cross close/midnight/30-day/complete-day boundaries while windows and original clock calls remain untouched. Test same-size replacement/rebinding, native row mutation via hook, append/remove/reorder, duplicate/conflicting settlement, invalid native fields, subclass/deepcopy side effects, exceptions at different row positions, nested calls and post-exception recovery. Preserve old unknown venue/history data and delayed fill/settlement cohort semantics.
* Retain fresh FULL and subsequent NORMAL practice saves, atomic receipt+state transaction, mirror-old-file survival, exact save ordering and crash recovery. No changes to live pre-send FULL journal, single risk writer, archive/state/journal atomic commit, stop/owner receipts or any financial control. Existing focused suites plus full repository checks/exact-byte independent review required before release.
* Compare original and candidate under the same frozen fixtures and separate clean/count/allocation modes, paired or interleaved where practical. Require actual total checkpoint wall/CPU improvement beyond run noise in representative multi-day cases, no hidden small-state penalty or unbounded memory, and identical outputs. Use the already-discussed no-repeatable>5% total regression/>10%peak-RSS-growth gates as diagnostic limits; inconclusive remains inconclusive. No production speed or profit promise follows from offline improvement.
* A speeddesk.py edit changes observer source fingerprint. Use the existing distinct-epoch mechanism without aliasing/relabeling/resetting history: preserve old5score archive and current-source0score/2unknown snapshot as its own predecessor, strict V2 restore and V1 unchanged. No schema/protocol/model change. Root handles source authorization, epoch verification and release/runtime checks under standing approval.

No architecture blocker prevents implementing this carefully bounded hypothesis. Exact candidate and adversarial tests may reveal blockers; acceptance cannot be inherited from this baseline review. EXEC and profitability remain OPEN.
