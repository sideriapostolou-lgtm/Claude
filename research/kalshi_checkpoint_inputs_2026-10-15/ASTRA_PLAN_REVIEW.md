## Material concerns to resolve before accepting results

1. **A paper setting is not a sufficient harness boundary.** SpeedRunner.__init__ calls live_factory unconditionally (`speeddesk.py:194`); disabling Kalshi does not skip that construction. Default feed_factory also constructs adapters. Inject inert feed AND live factories, disable arena and other optional runtime features explicitly, use direct Settings construction with a unique private temp data_dir and a fake clock, and block socket connection/name-resolution attempts. Do not run runner.run, engine/CLI entrypoints, Settings.from_env/load_settings, real client factories or real data directories. The fake live.panel should be deterministic and visibly labelled as omitted live-report cost. Fake feed factory must provide the harmless maker-window callback used at initialization. Constructor side effects must be counted outside the warmed profile. No secret environment inspection/copying into artifacts; the worker can run under a deliberately minimal environment.
2. **Resource limits need enforcement, not just observations.** Max 60 seconds means wall timeout around each child INCLUDING fixture setup/teardown, with kill/reap on timeout; RLIMIT_CPU alone is insufficient. Single child, no multiprocessing arena or detached workers. Track RSS; if RLIMIT_AS is used as an additional hard bound, label it address-space rather than claiming it is an RSS limit. Python/import address space may hit that cap before RSS; report such an abort rather than silently raising it. The 100 MiB cap must include db, WAL, SHM, mirrors, temp files, logs and retained profiles under the private experiment directory, not only final JSON. Check projected and observed disk between bounded passes; do not let an unbounded log sink defeat the cap. Keep fixtures small enough that one large SQL/JSON write cannot cross the remaining headroom. All limits are experiment limits, not assertions about Railway resources.
3. **Untimed preparation, counting, allocation instrumentation and actual latency measurements must be distinct.** asdict wrappers/cProfile/tracemalloc change timings. Report uninstrumented wall/thread CPU in repeated fresh or identically warmed runs, with a separate counting/allocation pass. Retain raw samples and sample count; a p95 from only a few samples is descriptive and weak. Shared-machine contention can move wall time: do not present synthetic wall-minus-CPU as storage cost or production causality. Stop when the cap is reached and label incomplete fixture cells.
4. **Initial history publishing is not steady-state saving.** First checkpoint pays FULL sync and creates every daily report/receipt; later saves normally use NORMAL and existing reports. Separate fresh ledger, historical report seeding, warmed unchanged-report checkpoint, and deliberately corrected-report checkpoint. Ensure warm-up actually stabilized reports under the fixed clock. Count attempted and committed receipts/transactions separately. Do not create fake receipt emissions just to make baseline slow. Do not compare a first-save baseline against a warmed candidate.

## Exact semantics a later reuse candidate must preserve

`SpeedRunner.summary` (`speeddesk.py:348–390`) derives daily counters, then recursively evaluates each VENUES entry for combined summary. In each venue summary it reads latency, iterates current desk.windows in insertion order, filters by venue and calls clock.now for EACH matching-venue window before deciding end eligibility, converts only eligible windows with asdict, converts every current closed settlement, evaluates evidence.coverage, samples as_of, separately samples complete_kalshi_day time for Kalshi, calls window_scorecard, appends availability, samples the old-report cutoff, and samples the enabled/today comparison. Source call order matters.

A cached prefiltered list or single checkpoint timestamp silently changes behavior near a window close, UTC midnight, coverage certificate end or the 30-day retention threshold. Preserve original predicates and clock calls at their existing evaluation points. The passed checkpoint(now) and subsequent clock.now values can already differ. A faster computation naturally reaches real-wall boundaries differently, so acceptance should compare identical scripted clock return sequences, not demand identical physical timing. Do not replace the script by a single frozen time in the behavior tests.

Eager all-window conversion observes rows the old summary would skip (future windows or other venues), may move an exception earlier than prior daily report/receipt creation, and may convert dictionaries before a later mutation. For a narrow candidate, reuse *conversion results* only, not filtering, coverage maps, scorecards, latency, counters, report output or clock values. Lazy population at the original conversion site is less invasive than building all rows at checkpoint entry. First measure the cost: replacing conversions but retaining scans may or may not matter enough.

Rows are mutable dataclasses. A cache keyed solely by slug, mapping length, list length, or (id(list), len(list)) cannot detect replacement/mutation. Repeated keys can alias objects; one object can appear under multiple mapping keys. Do not deduplicate windows or settlements or reorder rows: scorecard conflict detection and accumulation depend on the supplied sequence. A single synchronous production checkpoint has no await and no feed-task interleaving, but this is not license to move it to another thread or carry prepared rows to a later checkpoint. Existing callbacks/overrides/test fixtures may have mutation or reentrancy side effects.

Prefer an explicit invocation-local context with a bounded lifetime if a candidate is justified; a persistent runner attribute needs try/finally and nested-call stack discipline, and is wider than a plain local optimization. Exceptions at daily report, state-build, ledger or mirror stage must not leak a context into the next call. Calls to summary/daily_reports/panel OUTSIDE checkpoint, including initialization's legacy report migration (`:178`) and heartbeat generation, must remain correct and fresh. Nested calls must not steal the outer context. A successful nested operation that mutates inputs cannot make the outer operation reuse obsolete rows. If guarding unusual/subclass objects, the guard must not itself trigger property/hash/equality side effects earlier than baseline; conservative original-path fallback is safer than attempting generic caching.

`window_scorecard` consumes mappings but constructs its own normalized fill dictionaries; its dedup merge mutates those fresh local dictionaries, not evidence fill inputs. It keeps raw window mappings in its local cohort but does not mutate their fields, and builds fresh settlement aggregates. `WindowEvidence.coverage/availability/complete_kalshi_day` currently read passed rows and evidence without retaining or mutating the row dictionaries. This supports sharing native converted rows within one normal invocation, subject to the lifecycle/clock rules above; it does not establish a general immutability guarantee for all overrides. New report result containers must remain independent; changing one report must not rewrite another or cached source rows. Preserve intentional existing old-report aliasing rather than globally deep-copying output.

`daily_reports` visits days chronologically from started_at to the checkpoint's passed current day (`:393`). New day: build combined report, set mode/partial/started/reported timestamps, assign to reports, append speeddesk_daily. Existing day: compute both venues, compare exactly, replace only venues, set revised_at and append speeddesk_daily_correction when unequal. Do not batch, reorder, suppress or invent these receipts, and do not reinterpret combined historical counters. pending receipts already queued before checkpoint stay before newly generated daily receipts. record does a shallow outer payload copy; nested report alias behavior is already part of current evaluation/commit timing. Failures partway through several days can leave earlier in-memory reports/pending receipts while committing no new ledger state; a candidate must retain the established failure/retry behavior.

For old days beyond 30 days, summary FIRST computes current data and THEN overwrites prior latency and scorecard from saved history when present (`:371–377`). Skipping old-day computation is a different semantic optimization: it changes possible errors and current daily counter updates, and would need a separate review. Keep old known results, unknown old venue fields, evidence restore_error/clock_reversals, uncertified whole days and gap versus unknown distinctions. Late settlement remains assigned to window-end cohort; carry-over first fill may revise placement-day fill-rate without moving execution-day P&L. No unknown-to-zero conversion or fabricated coverage.

Existing optimization is already present: `KalshiLiveDesk.scorecard` (`speeddesk_live.py:2656`) groups live intents locally with exact-native guards and original lazy fallback; independent tests pin exotic mutation/error behavior. `window_scorecard` already groups fills by window. This experiment targets repeated PRACTICE dataclass input conversions, not those algorithms, risk conditions or live grouping. No changes to scorecard formulas, models, fees, thresholds, schema or protocol are proposed.

## Fixture counts must expose what is being measured

Record D = number of completed date keys actually visited, V = len(VENUES), C = len(desk.closed), W and W_venue_eligible, fills F, report count, serialized report/state/mirror bytes, pending receipts and total events. Labels '1 day' and '31 days' alone are insufficient; a '1 day' fixture with started_at today has D=0. With stable clock, D completed days plus current panel and both venues, the report path makes V*(D+1) venue summaries, and converts C settlements every time, even if one venue has no matching windows. Report settlement conversions are V*(D+1)*C. Model.to_state adds a separate C conversions from speeddesk_model's asdict, so count callsite/module separately. Stable eligible windows are converted (D+1)*sum(W_venue_eligible); window scans also examine mismatched venues but clock calls occur only for matching ones. If live.panel is stubbed, state that its real cost is excluded.

D, C, W and F co-grow if every fixture models 96 windows per day. Report-only repeated conversion then scales roughly quadratically in historical days; that is not proof that production has that size. Include at least one control that varies D with fixed C/W and one that varies C/W with fixed D. Both venue histories should be represented; empty/unknown venue cases belong in semantic controls. State whether 96 windows means per venue or total, and whether settlements are valid/idempotently constructed versus injected. Include missing coverage, mixed open/unresolved windows, quiet windows, partial maker/taker fills with fees, carry-over first fill and late settlement in bounded correctness fixtures; performance fixtures need not fabricate every one at full 31-day size.

Actual window fields and lists should have the same broad shape as production. Empty tape/metrics/live panel systematically understate total checkpoint work and inflate the fraction attributable to report conversion; disclose those omissions and, if resources permit, include bounded representative tape/metric payloads. Synthetic history can identify repeated work and improve offline cost; it cannot establish that this work caused the observed production gaps or that reducing it makes trading profitable.

## Root refinement: prefer settlement-only if measurement warrants it

Root's narrower suggestion is preferable to window caching. Window is a mutable dataclass (`speeddesk_model.py:105`); even the same Window object can be updated by a scripted clock or evidence hook between summaries. Leave all window filtering, conversion and clock calls unchanged in the first candidate. Settlement (`:421`) is frozen and has eleven nominally scalar fields, so native settlements are a more defensible conversion target. This does not authorize a patch before measurements.

Frozen is not a guarantee that arbitrary field values are immutable or properly typed. Python allows a string/number subclass, malformed nested value, dataclass subclass, missing field or even object.__setattr__ changes. The closed list itself is mutable and may append/rebind/reorder while retaining length. Guard exact Settlement class and exact scalar field types before admitting a fast path, with conservative original asdict fallback for exotic rows, and verify the current row contents/sequence at each original conversion site. A scalar signature can detect same-object changes without invoking custom equality/hash methods if its constituent types are exact builtins; it adds O(C) work that must be measured. Identity-only cache is inadequate as a generic contract, and whole-list id/length guards are inadequate even for frozen rows when replacement is possible. Guard access must not swallow or reorder baseline exceptions: malformed native objects need careful original-path behavior; do not scan every future row's fields before the first baseline row would be converted.

Lazy per-row reuse during the existing settlement list comprehension best preserves original row order and error timing. Keep a fresh list for every summary; reuse only dictionaries proven read-only by native consumers, or shallow-copy the cached flat dictionaries if result identity/isolation must be retained. Never return a cache-owned list that a later append could mutate retroactively. If evidence callbacks can mutate cached rows, choose isolation or fallback, not assumptions. Recheck count/signature overhead against asdict cost; an elaborate generic cache may erase the benefit. Preserve duplicate rows and conflicts; deduping settlement rows changes validation.

Extra fail cases: same-length closed-list element replacement; frozen row changed with object.__setattr__ via clock hook; exact Settlement holding a str/float subclass whose deepcopy raises or mutates another row; native missing field after an earlier valid row; same frozen row appearing twice; appended/removed row between summaries; row order reversed; nested checkpoint while cache exists; exception then next checkpoint; standalone summary after checkpoint. Compare baseline result, exception class/order, pending correction receipts, committed state and input object mutations, not only final report equality. A fallback should be explicit and tested; broaden scope only when measured evidence justifies it.
